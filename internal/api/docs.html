Introduction

ProvenGraph is a provenance graph for the agent economy - three product lines on one graph engine. Trust scores MCP servers on reliability and reputation. Knowledge tracks verifiable claims with attestation-weighted scoring. Memory stores purpose-tagged, GDPR-ready agent memories with retention policies.

Three Pillars

Trust

Description: Server registry with trust scores computed over a provenance graph. Who-do-I-trust, answered at runtime.

Purpose: Eliminate hardcoded server URLs. Agents resolve capabilities against live, probed endpoints ranked by uptime and outcome-verified reputation. The moat: outcome reports are weighted by the reporter's own trust - a throwaway agent can't pump a score.

Instructions: Register a server via POST /v0/servers. Health checks run every 60s. Agents resolve with GET /v0/resolve?capability=X. Report outcomes via POST /v0/outcomes.

Knowledge

Description: Verifiable knowledge claims with provenance scoring. Attestations from trusted orgs raise the score; contradictions and supersession lower it.

Purpose: Build a shared knowledge base where truth is not asserted - it's attested. Every claim carries provenance: who vouched, who contradicted, and whether it's been superseded by a newer version.

Instructions: Create a claim via POST /v0/knowledge. Attest to claims with POST /v0/knowledge/{id}/attest. Contradict or supersede claims to build the debate graph. Query with GET /v0/knowledge?domain=X.

Memory

Description: Purpose-tagged memory entires with compliance metadata - retention policies, consent tracking, and subject IDs. Built for the right-to-be-forgotten agent economy.

Purpose: Agents need memory that is searchable, auditable, and deletable. Every entry records why it exists (purpose), how long it lives (retention), and who it concerns (subject). Shared memory: multiple agents can remember the same entry.

Instructions: Create via POST /v0/memory. Agents remember with POST /v0/memory/{id}/remember. Forget with DELETE /v0/memory/{id}/forget?agent=X. Hard delete with DELETE /v0/memory/{id} - this is the right to be forgotten.

API Reference

Trust Endpoints

GET /v0/resolve?capability=X

Resolve servers by capability. Returns only healthy (UP) servers, ordered by uptime.

ParamDescription
capability requiredThe capability slug to resolve (for example sandbox, web-search, or mcp-server)
curl -s "https://provengraph.trucore.xyz/v0/resolve?capability=sandbox" | jq .
GET /v0/servers

List servers with filters and cursor-based pagination.

ParamDescription
queryFull-text search across name and description
capabilityFilter by capability slug
statusactive (default), delisted, or all
cursorPagination cursor from previous response
limitMax results per page (1-100, default 20)
curl -s "https://provengraph.trucore.xyz/v0/servers?capability=mcp-server&status=active&limit=10" | jq .
GET /v0/servers/{id}

Get a single server by its UUID.

ParamDescription
id pathThe server UUID
curl -s "https://provengraph.trucore.xyz/v0/servers/00047d75-8270-42f4-b79d-e3fc30db4510" | jq .
POST /v0/servers

Register a new MCP server. Returns a server_id and write_key - save the write key for updates.

ParamDescription
name requiredServer slug
description requiredHuman-readable summary
server_url requiredBase server URL
health_urlOptional health probe URL
probe_methodGET or POST
capabilities requiredArray of capability slugs
owner_contactContact point for updates
curl -X POST https://provengraph.trucore.xyz/v0/servers \
  -H "Content-Type: application/json" \
  -d '{
    "name": "my-mcp-server",
    "description": "My custom MCP server providing sandbox execution",
    "server_url": "https://my-server.example.com",
    "health_url": "https://my-server.example.com/health",
    "probe_method": "GET",
    "capabilities": ["sandbox", "code-execution"],
    "owner_contact": "ops@example.com"
  }'
PUT /v0/servers/{id}

Update server manifest. Requires X-Write-Key or Authorization: Bearer header. All fields are optional - send only what changed.

ParamDescription
id pathThe server UUID
X-Write-Key authWrite key returned during registration
curl -X PUT https://provengraph.trucore.xyz/v0/servers/{id} \
  -H "Content-Type: application/json" \
  -H "X-Write-Key: {your_write_key}" \
  -d '{"description": "Updated description"}'
DELETE /v0/servers/{id}

Delist (soft-delete) a server. Requires write key auth. The server is hidden from list/resolve but retained for history.

ParamDescription
id pathThe server UUID
X-Write-Key authWrite key returned during registration
curl -X DELETE https://provengraph.trucore.xyz/v0/servers/{id} \
  -H "X-Write-Key: {your_write_key}"
GET /v0/stats

Registry statistics: active/total servers, up count, 24h resolutions and probe counts.

curl -s "https://provengraph.trucore.xyz/v0/stats" | jq .
GET /v0/export

Full registry dump - all servers with current health state. Useful for bulk analysis.

curl -s "https://provengraph.trucore.xyz/v0/export" | jq .

POST /v0/knowledge

Create a claim. Returns claim_id and write_key.

ParamDescription

Get a claim with provenance score.

ParamDescription
id pathThe claim UUID

List and search claims.

ParamDescription

qFull-text search query
curl -s "https://provengraph.trucore.xyz/v0/knowledge?domain=agents&q=attestation" | jq .

Update claim. Auth: X-Write-Key. All fields are optional.

ParamDescription

  -H "X-Write-Key: {your_write_key}" \

Assert supersession. Auth: X-Write-Key. Marks the old claim as superseded.

ParamDescription

curl -X POST https://provengraph.trucore.xyz/v0/knowledge/{id}/supersede \
  -H "Content-Type: application/json" \
  -H "X-Write-Key: {your_write_key}" \

POST /v0/knowledge/{id}/contradict

Assert contradiction. Auth: X-Write-Key.

ParamDescription
id pathThe claim UUID
X-Write-Key authWrite key returned during creation
contradicts_id bodyThe claim being contradicted
curl -X POST https://provengraph.trucore.xyz/v0/knowledge/{id}/contradict \

Attest to claim. Body: {issuer}. Does NOT require write key - anyone can attest.

ParamDescription
id pathThe claim UUID
issuer bodyAttesting issuer label

  -H "Content-Type: application/json" \
  -d '{"issuer":"trusted-org"}'

Full ClaimBreakdown: attestation_score, freshness_score, contradiction_penalty, supersession_penalty, total (0-100).

ParamDescription

SDK Reference

Python

pip install meshdns-client
from meshdns_client import MeshDNS

client = MeshDNS("https://provengraph.trucore.xyz")
servers = client.resolve("sandbox")
for s in servers:
    print(s["name"], s["server_url"], s["uptime_30d"])
claims = client.create_claim(
    content="Agents should prefer attested claims.",
    domain="agents",
    issuer="acme.ai",
)
claim = client.get_claim(claims["claim_id"])
for item in client.list_claims(domain="agents", q="memory"):
    print(item["id"], item["provenance"]["total"])
memory = client.create_memory(
    content="User prefers concise answers.",
    owner="agent-7",
    purpose="support",
    subject="user:123",
)
entry = client.get_memory(memory["memory_id"])
for item in client.list_memories(agent="assistant-1", category="fact"):
    print(item["id"], item["purpose"])
client.remember(memory["memory_id"], agent_id="assistant-1")
client.forget(memory["memory_id"], agent="assistant-1")

Deployment

Single Binary

ProvenGraph ships as a single static Go binary with zero external dependencies. SQLite via pure Go - no CGo, no database server needed.

Docker

docker build -t provengraph .
docker run -d -p 8080:8080 -v ./data:/data provengraph

Configuration

PROVENGRAPH_PORT=:8080
PROVENGRAPH_DB=/data/provengraph.db
PROVENGRAPH_PROBE_INTERVAL=60s
PROVENGRAPH_PROBE_TIMEOUT=5s
PROVENGRAPH_WORKERS=8

Systemd

[Service]
ExecStart=/usr/local/bin/provengraph serve
WorkingDirectory=/var/lib/provengraph
Restart=always
RestartSec=5

Architecture

Stack

  • Go stdlib HTTP server - no frameworks
  • SQLite via modernc.org/sqlite - pure Go, file-based
  • Background health pool - configurable workers
  • Bearer token auth - write_key per registration

Graph Engine

The graph engine (internal/graph/) supports all three product lines: Service/Agent/Org nodes for Trust, KnowledgeClaim nodes for Knowledge, MemoryEntry nodes for Memory. One SQLite database, one binary, three products.

Data Flow

  1. Servers register via POST /v0/servers
  2. Background workers probe health URLs every 60s
  3. Agents query GET /v0/resolve?capability=X
  4. Only UP servers returned, ranked by uptime

Response Format

Every server object includes:

  • source / source_url - catalog provenance (MCP Registry, Smithery, npm, TruCore)
  • auth - public, auth-required, or unknown
  • tool_count / tool_names - tools pre-discovered from descriptions
  • curl_snippet - ready-to-use lazy MCP call command
